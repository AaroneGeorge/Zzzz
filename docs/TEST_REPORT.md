## Bugs and risks, ranked

### Blocker for the recording (operational, not a code bug)

**B1. The real app dir's daily budget is nearly gone.** `data/ledger.jsonl` now shows ₹577 spent today (my ₹239 run made it worse). ₹423 is left and `mobile_topup` is at ₹577 of its ₹600 cap. So the next ₹239 Jio will be DENIED, and the ₹700 Amazon Pay preset will be DENIED (₹700 > ₹423). Repro: `cd app && bun run demo -- "Recharge +919999999999 with ₹239 Jio"`. Fix: `bun run demo -- --reset-ledger` before recording, then restart `bun run serve` (the UI run list is in memory). I did not reset it myself. This does not affect judges, because the ledger is git-ignored and a fresh clone starts at ₹1,000.

### Medium

**H1. Headline claims overstate what is real.** The UI header says "An AI agent buys on Bitrefill with shielded ZEC" (`src/web/index.html` line 107). SUBMISSION's tagline is "An AI agent spending shielded ZEC at Bitrefill", and its Description opens "Shielded ZEC can pay for Bitrefill today through a viewing-key gateway". In fact the ZEC (testnet TAZ) goes to our own gateway wallet and the Bitrefill test order is paid from a free balance; Bitrefill does not accept ZEC. The "Limits" paragraph and the README table state this plainly, but a judge skimming the first line may read it as a real purchase. Fix: reword to "pays a Zcash testnet gateway that gates a Bitrefill test order" or add "(testnet, test products)" to the header, tagline and first sentence.

**S1. Web UI binds `0.0.0.0` with no authentication, and the docs do not say so.** Anyone who can reach the port can `POST /api/run` (spends testnet funds up to the budget) and `POST /api/confirm/:id` (answers the human-confirm prompt). `req.json()` ignores the content type, so a malicious web page the operator visits can send a no-preflight cross-site POST (CSRF) to `localhost:3000`. Run ids are `run-YYMMDDHHMMSS-xxxx`. The damage is bounded by the mandate and by testnet funds, but the Confirm control is the human-in-the-loop guarantee. Fix: default `HOST=127.0.0.1` (opt in with `HOST=0.0.0.0`), require `content-type: application/json`, and add one sentence to README (threat model).

**W1. A killed or Ctrl-C'd zingo session leaves the cross-process lock for 10 minutes.** Repro: `ZEC_WALLET=zingo bun run demo -- "..."`, send SIGTERM or Ctrl-C while it runs, then `ls .secrets/zingo-testnet/.zr-session.lock` still exists; the next run waits (stale limit 10 min, `src/wallet/zingo.ts` `acquireLock`, no signal handler). This will bite a recording retake. Fix: install `process.on("SIGINT"/"SIGTERM")` handlers that remove the lock, or store the PID in the lock and treat a dead PID as stale. Workaround: `rm -rf .secrets/zingo-testnet/.zr-session.lock` when no run is active.

**G1. "A denial is final" is enforced by the prompt, not by code.** `request_approval` is blocked only when its step is `ok`; after a DENIED (or a human reject) the step is `failed`, so the model can call it again with another amount and be approved. Reproduced with `AgentTools` and a fake model: a ₹1,500 request was denied; a second `request_approval` for ₹400 in the same run returned `approved:true`, and `run.status` stayed `"denied"` while the run could continue to pay. The mandate (budget, caps, allow-list) still holds, but the agent can spend a different amount than the user asked, the UI can show DENIED for a run that paid, and a model could re-ask the human after a rejection. ARCHITECTURE says "A denial is final". Fix: in `request_approval`, throw when `run.status` is `denied` or `rejected`.

**Z1. `ZEC_WALLET=zingo` without the Docker image hangs with no message.** On a fresh clone without `zecrecharge/zingo-cli`, the run stops silently at step 3 (the wallet address lookup runs `docker run`) for more than 45 s and has to be killed (exit 124). Fix: have `scripts/wallet-zingo.sh` or `zingo.ts` check `docker image inspect` and fail in under 5 s with "build the image: docker build -f docker/zingo.Dockerfile -t zecrecharge/zingo-cli ."; add a timeout. Judges can't use this path anyway (no funded wallet), so keep the README text saying so.

### Low

- **G2. Real-mode amount is not tied to the product price.** The gate checks the model-supplied `amount_inr`; `confirmOrder` orders `a.value ?? a.amountInr` from the product package. In `BITREFILL_MODE=real` a model could approve a small amount for a larger package. Only matters in real mode, which is off by default and creates only unpaid invoices. Fix: compare the package value with the approved amount before creating the invoice. Also: category is model-supplied (already stated in ARCHITECTURE "Limits").
- **L1. Empty or whitespace prompt in the CLI silently runs the default ₹239 Jio request and spends mock budget** (`src/cli.ts`: `... || "Recharge +919999999999 with ₹239 Jio"`). Fix: use the default only when no argument was given at all, and print a usage line for an empty string.
- **L2. Scripted parser turns a UK number into `+917700900123` and a UK brand into "Vi".** It fails later on "no rupee amount", with no mention of India-only. Fix: reject non-`+91` numbers and `£`/`$` amounts with "India only".
- **L3. Missing `ANTHROPIC_API_KEY` shows the raw SDK message** ("Could not resolve authentication method..."). Fix: check the key up front and print "AGENT_MODE=llm needs ANTHROPIC_API_KEY in .env; use AGENT_MODE=scripted without a key".
- **L4. Denied and failed runs exit 1, so `bun run` prints `error: script "demo" exited with code 1`.** For the ₹1,500 denial preset in a video this looks like a crash. Fix: exit 0 for DENIED (an expected outcome), or add a note.
- **L5. Header and chips show the requested wallet, not the effective one.** With `ZEC_NETWORK=mainnet ZEC_WALLET=zingo` (or any wallet init error) the CLI header prints `wallet=zingo` (and `network=mainnet`) while the real source is the fake wallet; the `note:` line and MOCK badges tell the truth, but the web chips (`c.walletKind`) do not. Fix: derive the chip from `sources.wallet` and show "mock (fallback)".
- **H2. A `✓` is drawn in front of "Caveat: the lightwalletd server sees our IP"** (`holds: true`), so a negative reads as a positive; in mock mode the same list shows `✕` for the positive facts. Fix: render caveats with a different glyph ("!" or "ⓘ") and avoid ✕ for "not applicable (mock)".
- **H3. The agent's closing text is shown as raw markdown** (`**Order:**`, `- ` bullets run together) in the UI, see `docs/img/ui-gateway-run.png`. Fix: render minimal markdown or strip it.
- **H4. "unlocked_by: gateway ..." and "the ZEC payment causes the purchase"** can be read as ZEC paying for the Bitrefill order. It is a gate in our own code. The wording is fine only because the disclaimers sit beside it; keep them next to every such claim.
- **H5. Legend says `real` = "live call / real money or real check"**. No real money is ever used in any mode by default. Fix: "live call or real check; no real money".
- **H6. `--json` prints the redemption code unmasked** (test codes only; the CLI note says so).
- **H7. SUBMISSION says "Tool annotations (`destructiveHint`) informed the gate design"**; the code never reads the annotations (only `docs/bitrefill-feedback.md` discusses them). Reword to "we noted that annotations are available".
- **D1. Doc leftovers.** README (at ~19:06): "73 tests" (92), "6/6 steps", the flow described as 6 steps with a self-transfer, `{{ZEC_TXID}}` and `{{VIDEO_URL}}` placeholders, "Not live-verified" Bitrefill test mode (it is verified), and the zingo row saying the send "does not pay Bitrefill" and is a self-transfer. ARCHITECTURE: six steps, self-transfer. SUBMISSION: `{{REPO_URL}}` and `{{VIDEO_URL}}` still open. `docs/integration.md` and `docs/VIDEO_SCRIPT.md` contain absolute `/home/lechuuu/...` paths. Re-check all of these after the docs agent finishes: `grep -n "{{\|73 tests\|6/6\|six steps\|self-transfer" README.md docs/*.md`.
- **Known and documented (not bugs):** with the key, the "Amazon Pay" preset matches `amazon-fresh-india` and buys `test-gift-card-code`; the 1Click quote falls back to a labelled fixture for tiny amounts (₹99).
